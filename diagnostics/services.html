机内服务与重启 ​

本页列出 H1 机内与 SDK 开发、控制和维护有关的 systemd 服务。依据整机固件 1.0.090.260901 的服务定义及启动入口核对，核对日期为 2026-09-10；其他固件或选配功能可能有所不同。

这里的 .service 是操作系统管理的后台进程，与 ros2 service list 中的 ROS 2 请求/响应接口不同。一个 systemd 服务可能同时启动多个 ROS 2 节点。

SSH 远程登录机器人 ​

先让电脑与机器人建立网络连接，再在电脑终端中根据连接方式执行对应命令：

连接方式连接准备SSH 命令
网线直连用网线连接电脑与机器人，确保电脑能够访问机器人网线地址 10.42.0.2ssh wlab@10.42.0.2
连接机器人 WiFi 热点电脑连接机器人提供的 WiFi 热点，热点侧机器人地址为 192.168.60.1ssh wlab@192.168.60.1
同一局域网机器人连接路由器 WiFi，电脑也接入同一局域网；使用机器人在该局域网中分配到的实际 IPssh wlab@<机器人实际IP>

第三种方式请将 <机器人实际IP> 整体替换为实际地址（包括尖括号）。可在网络配置工具「状态」页的「WiFi 连接」区域查看机器人 IP；网络接入方法见网络配置与 OTA。

登录用户名为 wlab，默认密码为 wlab。出现密码提示时输入密码并按回车；终端不会显示输入的密码字符，这是正常现象。如果设备密码已修改，请使用修改后的密码。

首次连接会提示确认 SSH 主机指纹，核对连接的是目标机器人后输入 yes。登录成功后，当前终端中的命令将在机器人上执行，例如查询整机版本：

bash
cat /opt/wlab/robot/VERSION
1

操作完成后输入 exit，退出远程会话并回到电脑终端。

操作前确认 ​

以下命令在机器人终端执行，需要相应的 sudo 权限。先结束正在执行的动作、导航和测试，使机器人处于安全静止状态，再重启相关服务；重启会中断该服务负责的控制或通信，不能作为急停手段。

不要一次重启全部服务。先查看状态和日志，确认故障对应哪个服务。OTA 进行中不要重启升级服务、主控或断电。

运动、感知与应用 ​

服务名提供的功能 / 启动入口重启命令

整机维护服务 ​

下面这些服务负责整机基础运行和维护。排查普通 SDK 话题问题时，优先定位前两节中的功能服务；维护服务按对应故障和技术支持指导操作。

服务名用途对应重启命令
master.service整机主控程序，由 master.sh 启动原生 master 和记录程序；不是 ROS 2 的 master.launch.pysudo systemctl restart master.service
update-robotic.service固件 OTA 升级守护进程；升级进行中禁止重启sudo systemctl restart update-robotic.service
journal-record.service系统 journal 日志记录sudo systemctl restart journal-record.service
log-cleanup.service日志清理维护sudo systemctl restart log-cleanup.service
sys-monitor.service系统状态监控sudo systemctl restart sys-monitor.service
debug_info_upload.service调试信息上传sudo systemctl restart debug_info_upload.service
rosbag_upload.serviceROS bag 上传sudo systemctl restart rosbag_upload.service

另外需区分以下服务，避免看到名字就直接启动：

  • hardware.service：启动时触发硬件 / udev 初始化的 oneshot 服务；完成后可以显示 inactive (dead)，这不等于硬件服务故障，不用于日常重启某个控制节点。
  • factory_test.service：核对设备上保留的独立测试入口指向 /tmp/factory_test_node，当时未运行；网页跑机工具应检查 h1_run_test.service。
  • h1_voiceagent.service：另一个可选语音代理服务，核对设备上处于禁用、未运行状态；它与 h1_voice.service 不同。按选配交付说明配置，不作为通用启动步骤。

查看状态、日志和重启结果 ​

以机械臂应用服务为例：

bash
# 先看运行状态、退出原因和当前进程
systemctl status application.service --no-pager -l

# 查看本次开机以来最近 100 行服务日志
sudo journalctl -u application.service -b -n 100 --no-pager

# 确认机器人静止、任务已结束后重启
sudo systemctl restart application.service

# 复查；正常常驻服务应为 active (running)
systemctl is-active application.service
systemctl status application.service --no-pager -l

# 持续查看日志，Ctrl+C 只退出日志查看
sudo journalctl -u application.service -f

restart 命令返回成功只说明 systemd 完成了操作，仍需检查进程是否持续运行，以及对应话题 / 功能是否恢复。常驻服务若反复退出后被拉起，应结合日志排查，不要反复重启掩盖问题。

部分模块使用文件日志，或设置了 StandardOutput=null；journalctl 不保证包含所有业务日志。诊断聚合服务通常还写入 /data/cache/log/h1_diagnostics.log；网页跑机工具可在「接口健康」中下载日志，见故障速查。

bash
systemctl list-unit-files --type=service --no-pager
systemctl list-units --type=service --all --no-pager
systemctl --failed --type=service --no-pager
systemctl cat application.service --no-pager
systemctl show application.service -p ExecStart -p FragmentPath -p ActiveState -p SubState
