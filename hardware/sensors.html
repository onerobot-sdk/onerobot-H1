NOTE

注意： 头部的 RGB 相机和 D435 的 RGB 相机是两个独立的设备，分别对应不同的话题。 头部的 RGB 相机提供广角视野，适合环境感知；而 D435 的 RGB 相机与深度数据配对，适合精确测距和物体识别。 手部的 RGB 相机可以选择安装为广角相机或 D435，默认配置为广角相机。

位置RGB 话题RGB 消息类型深度话题深度消息类型Info 话题
左侧/left/camera/rgbsensor_msgs/msg/CompressedImage（JPEG）/left/camera/depthsensor_msgs/msg/Image（16UC1）/left/camera/info
右侧/right/camera/rgbsensor_msgs/msg/CompressedImage（JPEG）/right/camera/depthsensor_msgs/msg/Image（16UC1）/right/camera/info

NOTE

帧率监控话题： 上述每个相机都额外发布 /<相机名>/camera/fps（std_msgs/msg/Float32，约 1Hz），表示该相机当前的 实测发布帧率（RealSense 为 RGB 流的发布帧率）。相机掉线或停止出图时该话题发布 0，可据此判断相机是否在线、是否掉帧。 对应话题：/head/camera/fps、/head2/camera/fps、/left/camera/fps、/right/camera/fps。

NOTE

相机话题 QoS（订阅前必看）： rgb 与 depth 使用 BEST_EFFORT（SensorDataQoS，高频图像流的标准做法）；info、depth_info、extrinsics 使用 RELIABLE。

⚠️ 订阅 rgb/depth 时，订阅端 QoS 必须为 best-effort（C++ rclcpp::SensorDataQoS() 或 rmw_qos_profile_sensor_data；Python qos_profile_sensor_data），或 SYSTEM_DEFAULT。若用默认的 RELIABLE 订阅，会因 QoS 不兼容静默收不到任何数据（不报错，就是没图）。

按需发布： rgb/depth 仅在有订阅者时才发布（节省 CPU）；订阅接入后首 1~2 帧可能略有延迟，属正常。

深度数据与对齐（D435） ​

D435 的深度话题 /<相机名>/camera/depth（16UC1）发布的是原始、未对齐到彩色的深度图。若需把深度与彩色像素对应起来（例如取目标物体的 3D 位置），由订阅端用相机内参/外参自行对齐。为此，每个带深度的相机（D435）额外发布两个静态标定话题（约 1Hz、RELIABLE）：

话题类型内容
/<相机名>/camera/depth_infosensor_msgs/msg/CameraInfo深度相机内参 K
/<相机名>/camera/extrinsicsstd_msgs/msg/String（JSON）深度→彩色外参 R/T + depth_scale

extrinsics 的 JSON 格式：

json
{
  "direction": "depth_to_color",
  "rotation": [r0, "...", r8],
  "translation": [tx, ty, tz],
  "depth_scale": 0.001
}
1

  • rotation：3×3 旋转矩阵，列主序（column-major）。
  • translation：平移向量，单位 米。
  • depth_scale：深度换算系数，米 = Z16 原始值 × depth_scale。

对齐 / 取 3D 流程（对深度像素 (u, v)）：

  1. z = Z16值 × depth_scale，用 depth_info 的 K 反投影出深度相机系下的 3D 点 P_d；
  2. 用 extrinsics 的 R、T 变换到彩色相机系：P_c = R · P_d + T；
  3. 用 /<相机名>/camera/info 的彩色内参 K 投影到彩色像素。

只需要目标几个点的 3D 坐标时，对那几个像素做上述反投影即可，无需整张对齐。

/lidar_status 状态码说明 ​

/lidar_status 由激光雷达驱动节点直接发布，用于让其他模块感知雷达当前健康状况。它与 /diagnostics 中的 lidar 项不同：/diagnostics 是由 /scan 频率间接推断在线/超时，而 /lidar_status 是雷达节点上报的状态，能区分超时、未启动等具体情况；且已在发布端做过去抖（见下方说明），可直接使用、无需自行做迟滞判断。data 为状态码：

data状态含义
0NORMAL雷达正常，/scan 正常更新
1ERROR驱动异常错误
2DATA_TIME_OUT点云数据超时（雷达掉线 / 断连，最常见的异常）
3DATA_WAIT正在等待数据；已在发布端去抖吸收，仅出现在启动后、收到首帧前（见下方说明）
4STOP驱动未启动
-1未知不在上述枚举内的兜底值
  • 发布频率：约 10 Hz，每个驱动循环发布一次当前状态。
  • QoS：Reliable + KeepLast(1) + Durability=TRANSIENT_LOCAL（锁存）。订阅方的 durability 必须设为 TRANSIENT_LOCAL，否则后启动时可能收不到最近一帧，表现为“订阅了却一段时间没数据”。
  • 雷达在启动 / 连接失败时驱动节点会退出进程，此时本话题不会建立。监控端应把“订阅不到 /lidar_status / 长时间无更新”本身也视为雷达异常。
  • 已在发布端去抖，可直接使用。 驱动以固定 ~10 Hz 的节拍轮询取点云，而雷达产生一帧点云的时刻与轮询节拍并不对齐：某次循环恰好取到新帧即 0，落在两帧扫描的间隙里没取到即 3。若直接上报，健康运行时本话题会在 0 ↔ 3 之间高频跳变。为省去每个订阅方各写一遍去抖，发布端已把瞬态的 3 吸收掉（沿用上一个非 3 的状态码再发布）。因此：
    • 运行期实际只会出现 0（正常）与 2（掉线）；3 只在启动后、收到首帧前短暂出现，1/4 正常运行中不会产生。判活直接看状态码即可：读到 0 即正常，持续（例如连续数秒）读到 2 才判定掉线，无需再自行做 0 ↔ 3 去抖。
    • 真掉线不会被过滤吞掉：驱动在超过 1 s 取不到新帧时会自行把状态升级为 2，而发布端去抖只吸收 3、绝不碰 2，掉线检测零延迟。
    • 想观察雷达劣化（转速偏低 / 丢帧等尚未彻底掉线的情况），请看 /scan 的实际发布频率或雷达转速，本话题去抖后不反映该趋势。

示例命令 ​

bash
# 查看相机信息
ros2 topic echo /head/camera/info

# 查看相机实测发布帧率（数值约等于 RGB 帧率；相机掉线时为 0）
ros2 topic echo /head/camera/fps

# 查看电池状态
ros2 topic echo /battery/state

# 查看激光雷达运行状态码（0=正常，2=数据超时/掉线，详见上文）
ros2 topic echo /lidar_status --qos-durability transient_local
